Define a job called streamChat. It takes your message, plus a way to report each piece of the reply as it arrives.

Knock on the door at /api/chat and wait. That address is the agent.

We are sending something, not just asking for a page. That is what POST means.

Send it.

POST Sending data to a server, rather than just requesting a page. Posting a letter, not reading a noticeboard.
JSON A plain-text way of writing structured data that both sides agree on. Almost every service on the internet talks in it.
/api/chat An endpoint — one specific address on the agent that handles one specific job.

Why the answer arrives in dribs and drabs

The agent does not wait until it has the whole answer. It streams each word the moment the model produces it.

1
Without streaming: 15 seconds of nothing

The screen sits blank, then the entire paragraph appears at once. It feels broken, so people press the button again.

2
With streaming: first word in 6 seconds

Same total time. But you can see it thinking, so you wait instead of giving up.

This was a real bug in this codebase. The switch that turns streaming on was left at its default — off — so one giant message arrived after a long silence. Turning it on changed one reply from 1 chunk into 269.

🕐
Perceived speed is a feature

Nothing got faster. Only the order changed. A large slice of performance work in real products is like this — not making the wait shorter, but making it visible.

📚

📝

📄

Write up what this conversation found as a PDF you can hand to somebody else.

✂️
Deliberately narrow

The underlying system offers far more than six operations. The agent hides most of them, because every extra option is another decision a small model can get wrong.

One class per job

Each capability is a single Python class. Three lines define what the model is shown.

CODE 

class Capability:
    """One tool: its schema, how to run it, and how to shape what comes back."""

    name: str = ""
    description: str = ""
    parameters: dict[str, Any] = {"type": "object", "properties": {}}
PLAIN ENGLISH

Here is the blueprint every tool is built from.

A one-line note for humans reading the code. The model never sees this.

 

name — what the model calls this tool when it wants to run it.

description — the job advert. This is what the model reads to decide whether this is the right tool. It is the most important string in the file.

parameters — the blanks the model has to fill in, and what is allowed in each. Engineers call this shape a schema.

Adding a seventh capability means writing one more class. The list the model sees, the menu in the interface, and the dispatcher that runs it are all generated from these classes automatically.

The advert is the behaviour

Here is the real description for the search tool. Read it as what it is: instructions to a candidate who will only ever see this paragraph.

CODE 

    description = (
        "Search all indexed video for moments matching a visual description. "
        "Use this whenever the operator asks to find, show or locate something. "
        "An attached video automatically restricts the search to that video."
    )
PLAIN ENGLISH

The job advert starts here.

Sentence one says what the job is.

Sentence two says when to apply — and names the actual words a person is likely to use: find, show, locate.

Sentence three heads off a mistake before it happens: do not ask which video, it is already handled.

That is the entire specification. There is no other instruction anywhere.

💡
Prose is configuration here

In ordinary software, behaviour lives in logic you can step through. In an agent, a large part of it lives in English sentences. Rewording a description changes what the software does — and no test will fail. This is the single strangest thing about building with models, and worth knowing before you instruct an AI to "just tweak the prompt".

03

The shipping container

Why the agent talks to a translator instead of talking to the video system directly.

A detour that looks like a mistake

The agent needs footage. The video system has an API that serves footage. So why is there a whole extra server in between?

🔌

Direct wiring

Agent calls the video API itself. Fewer moving parts — but every new client rebuilds the same knowledge, and only this agent can use it.

📦

A standard container

The tools are described once, in a shape any AI client understands. This agent uses them. So could a different one, tomorrow, with no new code.

Before shipping containers, every cargo was loaded by hand in whatever shape it came in. The container did not make ships faster — it made any ship able to carry any cargo.

📦
MCP

MCP is that agreed shape. The tool server in this project speaks it, which is why the tools are not locked to this one agent.

Never let the model do arithmetic it can fake

Asked for "since Tuesday", a small model will confidently invent a date — and it will be wrong roughly as often as it is right. So the tool takes "2" and "days" separately and works the date out in ordinary code. Give models judgement, not sums.

Everything on the wire is a labelled envelope

Coming back the other way — agent to browser — every single message has a type on the front. Steps, words, clips, errors, all the same shape.

04

The fact-checker

Search is confidently wrong a lot of the time. Here is what this codebase does about it.

A real result, from a real run

Somebody searched for "show me a car". Here is what actually came back.

12
candidate segments returned

Ranked by how closely each one matched. Every one of them scored well enough to show.

1
confirmed on inspection

A second look agreed: yes, that is a car.

2
rejected on inspection

Confident, high-scoring, and wrong. Two of the top three.

Nothing was broken. That is search working normally.

⚠️
A number worth carrying around

If you build anything that searches by meaning — documents, images, video, support tickets — expect a meaningful share of confident, well-ranked, wrong results. Plan for it in the design instead of being surprised by it in production.

Why it goes wrong

Searching here is not looking for words. Every video segment is turned into an embedding — a long list of numbers describing roughly what it looks like.

📍
Everything gets a position

Each segment, and your typed question too. Similar-looking things land near each other.

📏
Search means "what is nearest?"

Not "what contains this word". That is why plain English works at all.

🎭
Nearest is not the same as right

A red van sits very close to a red car. Nearest always returns something — even when nothing matches.

💡
This kind of search can never say "no"

Ask for the twelve nearest segments and you get twelve, always — even if your subject appears nowhere in the footage. The ranking has no notion of "none of these are it". Something else has to supply that judgement.

Sending it to the fact-checker

A newspaper does not print a reporter's claim because it sounds plausible. Someone checks it against the source first.

So the agent takes the frame nearest each top hit and asks the vision model a much narrower question. This second pass is called a critic.

CODE 

    prompt = (
        "You are verifying a video search result.\n"
        f'The user asked for: "{query}".\n'
        "Looking only at this frame, decide whether it genuinely shows that, "
        "and say which of these are visible:\n"
        + "\n".join(f"- {item}" for item in checkable)
        + "\nBe strict: if something is not clearly visible, it is not present."
    )
PLAIN ENGLISH

Build the prompt that goes to the vision model alongside the picture.

Give it one job, and say so first. It is not chatting, it is checking.

Quote what the person actually asked for, word for word.

"Looking only at this frame" — no guessing from context, no benefit of the doubt.

Then ask it to go through a checklist rather than give a yes or no.

The checklist itself: each thing that must be visible, as its own line.

And the whole trick, in one sentence. Without it, models are agreeable and say yes.

That is the fact-checker.

"Be strict" is doing an enormous amount of work here. A model asked "is this a red car?" wants to be helpful. It has to be told that unhelpful is the correct answer when the picture does not support it.

Three verdicts, not two

CODE 

CONFIRMED = "Confirmed"
REJECTED = "Rejected"
UNVERIFIED = "Unverified"
PLAIN ENGLISH

The checker looked and agreed.

The checker looked and disagreed.

Nobody looked — it ran out of budget, or the check failed. Crucially not the same as "rejected", and the interface says so.

🤔
"Unknown" deserves its own answer

Collapsing "we did not check" into "it failed" is one of the most common ways software lies to people. Any time you design a status, ask whether it needs a third value for we do not know — it usually does.

Why not check all twelve?

Because each check is a full look at a picture by the vision model, and the model server does them one at a time.

CRITIC_MAX_CLIPS=3 How many results get a second look. Raise it for accuracy, lower it for speed — this one setting is the whole trade-off.
CRITIC_ENABLED Turn checking off entirely. Faster, and every result becomes Unverified rather than silently trusted.

A slow or failed check never sinks the search. It returns Unverified and the results still arrive.

⚖️
Accuracy has a price, and it is time

This is the shape of nearly every quality decision in AI systems. There is no setting that is simply "better" — there is a dial between fast and right, and someone has to choose where it sits for their situation.

05

Watertight compartments

Real failures from this deployment — and why almost none of them were the agent's fault.

The agent is the last link

Behind the chat box sit roughly a dozen separate services: a model server, a tool server, a video pipeline, a database, an object store, a search index.

When any of them misbehaves, the operator sees the same thing: the agent found nothing.

🚢
Why ships have bulkheads

A hull is divided into sealed compartments so a breach floods one and the ship stays up. Software needs the same discipline: one failing dependency should degrade one feature, not sink the session.

Find the line that keeps the ship afloat

This code labels a video so searches can be narrowed to it. On one deployment, the labelling endpoint simply does not exist and returns "not found".

Click the line that stops that from breaking everything.

Which line saves the deployment?

1 try:
2 return await deps.client.add_video_tags(video_id, [uuid_tag(video_id)])
3 except VssError as exc:
4 logger.warning(
5 "Could not tag %s with its UUID; searches scoped to this video "
6 "will fall back to filtering by id: %s",
7 return []

Without those two words, one missing feature on one version of one service meant no video could be added at all. The failure was three services away from where it appeared.

💡
Decide what is essential and what is a bonus

Labelling was always a nice-to-have — it makes searches faster to narrow. It was written as though it were mandatory. Ask of every dependency: if this is missing, should the feature be worse, or should it be gone? Say which one you want when you brief an AI assistant, because it will not guess.

The gallery

Every one of these was reported as "the agent is broken". None of them were.

🏷️

"Nothing indexes"

A labelling endpoint missing on that version returned "not found", and the error travelled all the way up and killed the job.

👁️

"No detections, ever"

One missing stage in the video pipeline meant the object detector ran perfectly and its output was thrown away silently.

🔢

"0 of 8 indexed"

Whether a video is searchable was being worked out from live progress data. Restart the service, lose the progress, and eight indexed videos read as zero.

🔌

"Every search is empty"

One service wedged its own database connection. Its health check still answered "fine" while every real query hung.

🩺
Health checks lie

That last one is worth remembering. A service reporting healthy usually means "the process is running", not "the work succeeds". When something is wrong, test the actual job, not the status light.

The worst kind: it worked yesterday

Users reported that search sometimes just… did not happen. The agent would answer in words instead of searching. Same question, different day, different behaviour.

The same request was sent eight times, unchanged:

5
of 8 identical requests ran a search

The other three answered in prose. Nothing differed but chance.

8
of 8 after one setting changed

Turning the model's randomness down to zero. Same prompt, same tools, same everything else.

Models pick their next word with a controlled amount of randomness, set by a dial called temperature. That is lovely for prose and disastrous for decisions — and "shall I run a search?" is a decision.

🎲
Separate the choosing from the writing

When an AI feature works intermittently with no pattern, suspect sampling before you suspect your prompt. A tool that runs 60% of the time does not look random to a user — it looks broken.

A bug worth studying

Before summarising, the agent asks three questions: what is this footage of, what should be called out, what to keep an eye on. The operator answers. Then the agent replied:

💬
"I need you to specify which video you'd like summarized."

It had just been told. Twice.

Two independent causes, stacked:

1
The attachment was dropped

Answering re-sends the original message — but sending had already cleared the attached video, so the retry arrived with no video at all.

2
The model read its own question back

Its last remark in the history was "tell me what to look for". Seeing that, it asked again. No amount of instruction talked it out of it.

The second fix is the interesting one: the question is now left out of the conversation the model reads. It was never an answer — it was a form.

🪞
Models imitate the conversation they are shown

A model that sees itself asking a question will ask it again. If your AI feature repeats itself in a loop, look at what you are putting in its history before you look at your instructions.

A measure you can use anywhere

What you now know how to ask for

Six modules, and the point of all of them was to make these sentences sayable.

"add a capability" Not "add a feature" — one class, and the tool list, the menu and the wiring follow from it.
"degrade, do not fail" This optional service being down should make the feature worse, not absent.
"set temperature to 0 for tool decisions" Stop the choice of whether to act being sampled at random.
"verify before showing" Check the top results against the source before presenting them as answers.
"give unknown its own state" Do not fold "not checked" into "failed".
"stream the response" Send it as it is produced rather than in one lump at the end.
🗣️
Vocabulary is the leverage

You do not need to write this code. You need to be able to name what you want precisely enough that an assistant builds the right thing — and to notice when it has not.
